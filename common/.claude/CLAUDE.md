# CLAUDE.md

## 応答の言語

- ユーザーへの応答は日本語で書く。作業の途中経過の短い報告、最終報告、ツール呼び出しの合間の文章も含めて、セッションの最初から最後まで日本語にする。ツールの出力やコードが英語でも切り替えない。

## ツール

- ファイルの読み書きは Read / Edit / Write tool で行う。シェルの cat・sed・スクリプトによる一括置換で代替しない（壊れやすく、何をしたかが差分に残らない）。
- 改名・呼び出し階層の調査・構造検索は PhpStorm MCP を使う（`rename_refactoring` / `analyze_calls` / `search_symbol` / `get_symbol_info` / `search_structural` / `search_text` / `get_file_problems`）。スキーマは ToolSearch で `select:mcp__phpstorm__<名前>` として読み込む。PHP・TypeScript の両方で動く。
- 検索は問いの種類で使い分ける。MCP の検索は一致内容ではなく座標を返すため Read が follow-up で必要になり、リテラル検索では Grep より token と時間を食う。一方 Grep では記号の解決に届かない。
  - リテラル・ファイル名・「この文字列がどこかにあるか」は Grep / Glob。シェルで書くなら `grep` より `rg`。
  - 既存の命名や実装の慣例、型、呼び出し元は MCP。慣例を探すときは `search_symbol` に語の断片を渡す（`Input` で `...InputParam` の慣例に行き当たる）。`search_structural` は当て推量のパターンだと空振りするので、`get_structural_patterns` で確かめてから使う。
  - `analyze_calls` の `symbolFqn` は呼び出せるもの（メソッド・関数）に限る。クラスの FQN を渡すとエラーになるので、クラスの使用箇所は `search_text` で探す。
- 改名は `rename_refactoring` を使う。手で置換すると参照を取りこぼす。ただし追随しないものがあるので、実行後に次を確認する。
  - ファイル名。クラス名の変更後は `git mv` してオートロードを確認する。実行後のファイルは Edit の前に読み直す。
  - DI 設定などの YAML に書かれた FQN。名前空間が落ちた値に壊れることがあるので、設定ファイルの差分は必ず見る。
  - 似た名前の private メソッド。`read` を改名しても `readOccurredAt` は残る。
  - 同じ名前のローカル変数・引数が複数のメソッドにあるファイル。`symbolName` だけでは対象を絞れず、一部（PHPDoc の `@param` だけ、など）しか改名されないことがある。差分を見て、足りなければ戻してから Edit で直す。
  - テストクラス名とテストメソッド名の接頭辞（`request_...`）。クラスを改名しても `...Test` のクラス名は残る。
  - 改名した箇所の周りの整形。コンストラクタの引数が型と変数名の間に空白を詰めて揃えられることがあり、リポジトリの formatter では戻らない。差分を見て Edit で戻す。
- 編集直後に流れてくる IDE の diagnostics は、再インデックス前だと当てにならない（ファイル末尾を越えた行番号、削除済みクラスへの参照）。整形と静的解析は各リポジトリのコマンドの結果を正とする。
- PhpStorm MCP に接続できない場合、ユーザーに PhpStorm の起動を依頼する。
- git worktree はリポジトリ内の `.worktree/<ブランチ名>` に作る。作業ディレクトリの中に置けば、ファイルアクセスの許可を待たずに済む。
- PhpStorm MCP は PhpStorm で開いているプロジェクトにしか使えない。git worktree で作業するときは、その worktree を別のプロジェクトとして開くようユーザーに依頼する。言語レベルとインデックスは開いたプロジェクトの composer.json と vendor で決まる。
  - worktree を開いていないまま `projectPath` に worktree を渡すと、エラーにならず、同じ相対パスのメインの作業ツリーのファイルが書き換わる。worktree で MCP を使う前に、ユーザーが worktree を開いたことを確かめ、実行後はメインの作業ツリーの `git status` も見る。
- セッションの中で使い方を指示されたり新たに発見した場合は、次回以降使えるように反映する。`~/.claude/CLAUDE.md` は生成物なので、元の `~/Projects/src/github.com/okashoi/dotfiles/common/.claude/CLAUDE.md` を編集し、`install.sh` を実行する。

## コミット

- 「〜を切り出す」「〜を追加する」のように、独立して読める単位に分ける。1つのタスクの成果物をまとめて1コミットにしない。
- 原則、コミット毎にビルドや静的解析、テストがパスするような単位で分ける。
- 自動生成物は、生成元を変更したコミットに含める。
- レビュー指摘の反映も指摘ごとに分ける。「レビュー指摘を反映する」の1コミットにまとめない。
- 何をどう分けるかは手を入れる前に決める。分ける順序は、後のコミットで捨てる変更を前のコミットで作らないように選ぶ。
- コミットメッセージの本文は、修正の理由と目的を3〜4行で書く。調査で分かった機構の説明はプルリクエストの本文に置く。

## 文章（コードコメント・コミットメッセージ・ドキュメント）

読み手はその場の対話を知らない、という前提で書く。書いたあと一文ずつ「対話を知らない人に何を伝えるか」を確かめ、答えられないものは消す。

- コードから読み取れること、そのコードの責務外の情報は書かない。残すのは設計上の意図、外部仕様の制約、アルゴリズム名、コードに現れない前提だけ。
- 同じ内容を言い換えて繰り返さない。要点は一箇所で書き切る。
- 指摘への応答、依頼文の引用、比較検討で枝刈りされた情報、差分（「〜は変更しない」）、未決事項を持ち込まない。今どうであるかを書く。
- 理由は実際の理由だけを書く。一般的な慣行を固有の制約のように書かない。書けないなら事実だけにする。
- 仮実装・実装計画・作業状況は issue やプルリクエストに書き、恒久的な設計ドキュメントに入れない。仮実装はコード側のコメントから issue を参照できるようにする。
- 多重否定は肯定の表現に直せないか試す。直せるなら肯定形で書く。
- 語法は既存のものを使う。名詞や熟語に「させる」「する」を付けて言い回しを作らない。
- 抽象化して縮めた語（「セッションプロバイダ」など）を作らず、実体を普通の言葉で書く。外部サービスはその役割を1語で表す（「ビデオ通話を提供するサービス」）。節を重ねた説明文にもしない。
- 読み手の判断が残る表現ではなく、読んで行動が決まる形に書く。

## プルリクエスト

- 読み手が本文より先に知る必要がある前提（依存するPR、ベースブランチ、マージ順）は冒頭に置く。
- 本文には、レビューするうえで知っておくべき、コードから読み取れない意図だけを書く。何のための変更か、外から見た振る舞い（API の入出力など）がどう変わるかがこれに当たる。追加したメソッド、置き換えた箇所、例外の扱いといった実装の説明は、コードを読めばわかるので書かない。
- 指定がない限りドラフトで作成する。
- GitHub に書く文章（プルリクエスト・issue・コメント）では、URL の直後にマルチバイト文字を続けない。GitHub はそれを URL の一部として解釈し、リンクが壊れる。URL の直後には半角スペースを入れるか、半角の記号で区切る。
